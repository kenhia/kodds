## Scoring core (#3188)

- `kodds.scorer.Scorer` over a two-method `Backend` protocol (`tokenize`,
  `continuation_logits`), so the maths is tested with a fake bigram model and
  `just check` needs no weights. `kodds.llama.LlamaBackend` is the real one;
  `kodds.llama.load(path)` returns a ready scorer.
- **A choice's score is the summed log-prob of all its tokens, plus the
  end-of-turn token `<|im_end|>`.** The sum handles multi-token choices and
  shared first tokens (`k-homelab` is five tokens; five of the eight routing
  projects start with the bare token `k`, so a first-token reader cannot tell
  them apart at all). The terminator is the decision worth recording: without
  it a choice that is a prefix of another ("o" vs "ok", "Mars" vs "Mars bar")
  wins for free, because every continuation of it counts toward it. With it,
  the score means "the answer is exactly this". `end_of_turn=None` turns it
  off; a test pins both behaviours.
- Thinking disabled by rendering Qwen3's template exactly as
  `enable_thinking=False` does — an empty `<think>\n\n</think>\n\n` block —
  rather than via `/no_think`, so the next token is the answer.
- The prompt is evaluated once per call; each choice rewinds `n_tokens` to
  the prompt's end (`Llama.eval` drops KV from there) and evaluates only its
  own tokens. A GPU test checks the warm path against a cold evaluation.
- Log-softmax in numpy float64 over the ~152k vocabulary; pure Python was
  the first draft and would have cost ~30 ms per row.
- Tests: 7 model-free in `just check`; 3 marked `gpu` and deselected by
  default (`addopts = -m 'not gpu'`), run with `just test-gpu` /
  `KODDS_MODEL=…`.
- CUDA build: `CMAKE_ARGS="-DGGML_CUDA=on -DCMAKE_CUDA_ARCHITECTURES=89"`
  with the CUDA 13.2 toolkit already on kubs0 — no system packages needed,
  so nothing for record-machine-change. uv caches the built wheel; a fresh
  machine must build with those `CMAKE_ARGS` or it gets a CPU-only wheel.
- Models live in `~/models/gguf` (`KODDS_MODELS` overrides), outside the
  tree; `just models` fetches the four candidates.

## Eval set (#3189)

`evals/evalset.jsonl`, 154 items, generated by `evals/build_evalset.py`
(the JSONL is committed; the script is the reviewable source):

- **route** (64) — which of 8 korg projects owns a work item: 8 real titles
  each from klams, korg, kaed, k-homelab, kmon, karc, kvllm, kpidash, with
  korg's own routing descriptions in the prompt. A few titles lost a leading
  self-naming token (`kmon: …`, `kaed --version`) so the answer isn't
  spelled out; titles that name *another* project (kpidash's "klam's service
  card …") were kept as the hard cases.
- **severity** (45) — kmon's three-way call `ok` / `attention` / `problem`,
  15 each, findings written in kmon's shape and labelled by hand against the
  rubric in `kmon/controller.py`. homelab-health items don't record the call
  kmon made, so there was no real ground truth to copy — these labels are
  mine.
- **triage** (45) — legitimate / spam / phishing, 15 each, synthetic.

## Bake-off (#3190)

`evals/bakeoff.py <gguf>` runs one model per process and writes
`evals/results/<model>.json`; `evals/report.py` prints the comparison;
`just bakeoff` does all four. It refuses to start unless both TEI routers are
on the GPU and records whether their pids survived the run.

Run 2026-09-24 on kubs0 (RTX 4080 SUPER, 16 GB; llama-cpp-python 0.3.35,
CUDA 13.2, all layers offloaded, `n_ctx=1024`). Baseline 2,883 MiB — the two
TEI routers — before every run, and **both TEI pids were untouched after
every run**. Latency is one full `score()` call (prompt + all choices; 3
choices for severity/triage, 8 for route).

Reading it:

- **Everything fits beside TEI.** The largest, 14B Q4_K_M, peaks at 11.6 GiB
  on the whole GPU — ~4 GiB of headroom on a 16 GiB card. Nothing needed
  kai's 5090.
- **Size beats bits.** 8B Q8_0 is indistinguishable from 8B Q6_K (Brier
  0.601 vs 0.614 on 154 items is inside the noise) for 1.7 GiB more; 14B at
  Q4_K_M beats both on every metric and every task.
- **Every model is overconfident, and it is mostly fixable.** Mean top-choice
  confidence is ~0.96 across the board against 55–75% accuracy. A single
  temperature per model (fitted on half the items, scored on the other,
  both ways) cuts Brier by 18–38%; the fitted T is ~10 for all four. So the
  raw probabilities are a *ranking* worth having but not yet numbers to
  threshold on — a calibration step is the next thing that makes them the
  product.
- **Routing is the hard task, for every model** (28–47%, confidently wrong).
  From a title and eight one-line routing contracts, the models lean on the
  generic-sounding projects (kmon, k-homelab, korg). A diagnostic on the 4B
  confirmed this is the model's choice, not a scoring artefact: the raw
  summed log-prob of its wrong pick is ~0, i.e. it puts essentially all its
  own mass on the full name it picks. Severity and triage are where kodds is
  already useful (14B: 91% / 98%, ECE 0.08 / 0.03).
- ECE over 10 bins on 45–64 items per task is noisy; Brier is the number to
  lean on.

### Decision — default model: Qwen3-14B Q4_K_M

Best accuracy (0.75), best Brier raw and after temperature (0.488 → 0.399),
best on each task, and it fits beside klams' embedders with ~4 GiB spare at
~95 ms p50 per call. The cost is VRAM — the most of the four, ~4.4 GiB left
on the card — so if klams' embedders grow, **8B Q6_K** (9.3 GiB peak,
~6.7 GiB left, Brier 0.614 → 0.415) is the fallback — it gives up about 9 points of
accuracy, and nothing else here earns its place: 4B trails everywhere, and
8B Q8_0 buys nothing over Q6_K.

## Follow-ups

- **Calibration** (roadmap, Later → Next): per-task temperature scaling;
  the evidence above says a single T already recovers a third of the Brier.
- **Routing input**: title-only routing is the weakest thing measured.
  Before any korg-routing consumer ships, try the WI's content plus the
  project's full description, and a few-shot prefix — prompt work, not
  model work.
